# Telegram AI Operator — обновление и запуск

1. Выполни целиком `database/schema.sql` в Supabase SQL Editor.
2. Убедись, что в Railway запущена одна Replica и один сервис использует этот `BOT_TOKEN`.
3. Замени файлы проекта архивом и выполни Deploy.
4. В Railway Variables должны быть `BOT_TOKEN`, `ADMIN_ID`, `API_ID`, `API_HASH`, `TELEGRAM_SESSION`, `GROQ_API_KEY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
5. После запуска открой управляющего Telegram-бота и отправь `/status`, затем `/session`.
6. Добавь контакт через «Контакты» или `/add @username` / `/add TELEGRAM_ID`.
7. Только после фактического согласия подтверди его через «Подтвердить согласие» или `/consent @username` / `/consent TELEGRAM_ID`.
8. Включи ИИ в панели.

## Что изменено

- Удалены плановые инициативные сообщения; инициатива остаётся только внутри активного диалога.
- Добавлено объединение серии сообщений в один ответ.
- Добавлена очередь с сохранением Telegram ID входящих сообщений в Supabase и восстановлением после перезапуска.
- Ошибки генерации и отправки больше не приводят к немедленному удалению задачи: обработка повторяется.
- Панель управления расширена: уровни поведения, длина и формат ответов, интервалы объединения, модели Groq, API Key, диагностика, память, статистика, чёрный список, профили поведения, история системной инструкции, тестовый режим и резервные копии.
- API Key, введённый через панель, хранится в Supabase в зашифрованном виде и не показывается повторно.
- Контакт разрешён только при наличии записи в allowlist и `consented=true`.

## Важно

Точное время ответа до 15 секунд — целевой показатель, а не гарантия: задержки Groq, Telegram, сети и повторные попытки могут его увеличить. При обновлении Railway может быть короткий перерыв; код ожидает освобождения блокировки старым процессом до 3 минут, но время переключения контролирует Railway.

## Модуль ИИ-трейдера (первый исследовательский этап)

В текущую панель добавлен раздел «📈 ИИ-трейдер». Он работает отдельно от переписки и выключен по умолчанию.

- Источник котировок: публичные endpoints Binance USDⓈ-M Futures (`/fapi/v1/klines`, `/premiumIndex`, `/openInterest`). Для чтения данных API-ключ и аккаунт биржи не используются.
- Первый инструмент: BTCUSDT, таймфрейм 15m.
- Базовая исследовательская логика: пересечение EMA 9/21 с фильтром RSI 14; ATR-стоп; целевое отношение прибыли к риску 2:1.
- Сделки виртуальные. Модуль не содержит кода отправки реальных ордеров и не запрашивает биржевые секреты.
- Виртуальный стартовый баланс: 10 000 USDT; расчётный риск на сделку: 0,5%; условная комиссия: 0,05% за сторону. Это тестовые допущения, а не тариф биржи.
- Если стоп и цель задеты внутри одной свечи, симулятор консервативно считает, что первым сработал стоп.
- Цикл запускается только в единственном экземпляре приложения после получения существующей Supabase lease. Автоматическая торговля включается администратором кнопкой.

### Миграция

Повторно выполни обновлённый `database/schema.sql` в Supabase SQL Editor. Все новые таблицы создаются через `IF NOT EXISTS`; существующие таблицы и настройки не удаляются.

### Управление

Открой «📈 ИИ-трейдер» → «▶️ Запустить демо-трейдинг». Доступны ручной анализ рынка, статус и история сделок. Для остановки новых входов нажми «⏸ Остановить демо-трейдинг».

### Ограничения

Это не обученная нейросеть и не доказанная прибыльная стратегия. Это минимальный воспроизводимый baseline для сбора статистики и дальнейшего тестирования. Публичный Binance API здесь используется только как источник рыночных данных; это не означает, что Binance разрешает резиденту РФ открывать фьючерсный торговый аккаунт. Перед любым реальным исполнением потребуется отдельно подтвердить официальную доступность биржи и продукта для пользователя. Реальное исполнение в этой версии намеренно отсутствует.

## Обновление поведения ассистента и параллельных диалогов

В этой версии меню «Поведение» и «Ответы» объединено в раздел «Стиль и ответы». В разделе «Инструкция» доступны просмотр и изменение основной инструкции, отдельный блок дополнительных правил, тестирование ответа и история версий.

Ключевые ограничения владельца применяются отдельным приоритетным блоком поверх сохранённой инструкции: общение на «ты», женский род по отношению к собеседнице, отсутствие инициативного раскрытия ИИ, естественная манера без автоматических приветствий и избытка восклицаний. Поэтому ранее сохранённая в Supabase инструкция не должна отменять эти правила.

Для одновременных диалогов сохранены независимые очереди контактов. Общие запросы к Groq проходят через адаптивный ограничитель параллелизма: при перегрузке провайдера нагрузка снижается, после серии успешных запросов постепенно повышается. Начальный лимит по умолчанию — 4 одновременных запроса, максимум — 12. Его можно изменить переменной `AI_MAX_CONCURRENT_REQUESTS` (1–12).

При сбое основной модели используются заданные ранее заданные резервные модели. Если и они не сработали, приложение запрашивает список доступных моделей Groq и пробует до четырёх дополнительных кандидатов. Список не загружается перед каждым обычным ответом, поэтому первичная генерация не задерживается обнаружением моделей.

Новые параметры сохраняются в существующей таблице `operator_settings`. Отдельная SQL-миграция для этой версии не требуется. После обновления кода достаточно дождаться перезапуска Railway; затем открыть `/start` в управляющем боте.
