# Telegram AI Operator — обновление меню и планировщика

## Важно перед обновлением

1. Сделайте резервную копию текущих `app.py` и `database/schema.sql`.
2. Замените `app.py` в корне репозитория.
3. Выполните обновлённый `database/schema.sql` целиком в Supabase SQL Editor.
   Скрипт рассчитан и на существующие таблицы: добавляет недостающие столбцы и новую таблицу состояния.
4. Дождитесь успешного деплоя Railway.
5. Напишите управляющему боту `/start`.

## Новое меню

- Включить / выключить ИИ.
- Управление контактами.
- Просмотр / изменение / сброс инструкции.
- Управление инициативными сообщениями.
- Статус сервиса.

## Планировщик

- По умолчанию первое инициативное сообщение — через 6 часов после последнего входящего сообщения.
- Проверка примерно раз в 60 секунд.
- Без тихих часов.
- Не чаще одного инициативного сообщения за 24 часа на контакт.
- Временные отметки сохраняются в `operator_contact_state`; содержимое переписок не сохраняется.
- Для минимизации повторов время попытки фиксируется до отправки. Если Telegram/Groq временно недоступны в момент попытки, это сообщение может быть пропущено до следующего входящего сообщения.
- Запускайте только один экземпляр Railway-сервиса (одна реплика), иначе два процесса могут одновременно планировать отправку.

## Согласие

После добавления контакта он по умолчанию не активен для ИИ. Сначала получите его явное согласие на обработку сообщений ИИ, затем в меню «Контакты» нажмите «Подтвердить согласие» и введите `@username`. Можно также использовать `/consent @username`.

Команды `/add`, `/remove`, `/list`, `/prompt`, `/enable`, `/disable`, `/status` сохранены.

## Проверка

1. `/start` — появилось меню.
2. «Контакты» → добавить тестовый аккаунт.
3. Получить согласие собеседника и отметить его в меню.
4. Включить ИИ.
5. Проверить обычный ответ.
6. Проверить, что после 6 часов тишины появляется не более одного инициативного сообщения.
7. `/disable` — останавливает и автоответы, и планировщик.

## Ограничения MVP

Планировщик не является транзакционной очередью с гарантией доставки. При аварии в момент отправки возможен пропуск инициативного сообщения; механизм фиксирует попытку заранее, чтобы не создавать дубликаты после рестарта. Для строгой гарантии доставки потребуется отдельная очередь/outbox и атомарные операции в БД.


## Исправление ошибки Groq model_not_found

- Причина ошибки из Railway: `llama-3.3-70b-versatile` возвращает HTTP 404 для используемого API-ключа.
- Модель по умолчанию изменена на `llama-3.1-8b-instant` — быструю модель из актуального каталога Groq.
- Добавлен автоматический резервный перебор `openai/gpt-oss-20b` и `llama-3.3-70b-versatile`, если Groq отвечает ошибкой 404 на выбранную модель.
- В Railway можно задать `AI_MODEL` и `AI_MODEL_FALLBACKS` (список ID через запятую). Если переменная `AI_MODEL` уже задана в Railway, она имеет приоритет над значением по умолчанию. Для применения новой модели удали старое значение `AI_MODEL` либо замени его на `llama-3.1-8b-instant`.
- Идентификаторы моделей и их доступность могут зависеть от API-ключа и текущего каталога Groq. Официальный каталог: https://console.groq.com/docs/models


## Исправление запуска и блокировки экземпляра (2026-11-12)

Причина предыдущего падения: Supabase Python SDK не поддерживает цепочку `.update(...).select(...)` для используемого `SyncFilterRequestBuilder`. Блокировка теперь реализована через атомарные PostgreSQL RPC-функции; в Python-коде нет `.select()` после update.

### Обязательный порядок обновления

1. Supabase → SQL Editor → выполнить ПОЛНОСТЬЮ обновлённый `database/schema.sql`. Он идемпотентен: создаёт таблицу `operator_runtime_lock` и три RPC-функции `claim_operator_runtime_lock`, `renew_operator_runtime_lock`, `release_operator_runtime_lock`.
2. Подождать завершения SQL без ошибок.
3. В Railway оставить одну Replica и один сервис, использующий этот BOT_TOKEN.
4. Обновить `app.py` в GitHub (или загрузить весь архив) и выполнить новый деплой.
5. Убедиться по логам, что есть `Singleton lease acquired`, `Telethon connected` и `Starting aiogram polling`.

Блокировка атомарно захватывается в PostgreSQL; второй процесс не сможет начать polling. Аренда продлевается раз в 30 секунд, срок — 120 секунд. При потере аренды приложение останавливает polling. Health endpoint запускается до внешних подключений, поэтому Railway получает ответ даже во время старта.

### Проверки, выполненные при сборке

- Python compile check.
- Проверка целостности ZIP.
- Проверка отсутствия `.select("owner_id")` в логике блокировки.
- Проверка единственного `dp.start_polling()` и единственного обработчика входящих сообщений.
- Входящее событие передаёт сам Telethon event в `build_context`, чтобы использовать access hash первого сообщения.
- Убрана искусственная задержка debounce; timestamp Supabase записывается в фоне.

Если SQL не выполнен, приложение остановится с понятным сообщением о недоступной RPC-функции, а не с неясным AttributeError.
